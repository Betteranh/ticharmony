## État actuel

- Monorepo en place (`apps/api` NestJS+Prisma+Postgres, `apps/web` Next.js, `packages/shared`).
- Modèle de données Prisma : `Tenant`, `User`, `Category`, `Ticket`, `TicketComment`, `TicketAttachment`, `Notification`, `KnowledgeArticle`, `Asset`, `AuditLog` + enums rôles/statuts.
- Multi-tenant via RLS PostgreSQL opérationnel (rôle owner vs rôle applicatif restreint). **Rappel local** : Postgres/Redis tournent dans Docker Desktop — s'il n'est pas démarré, l'API répond 500 et la page de login web affiche à tort "Identifiants invalides" (le proxy `apps/web/src/app/api/auth/login/route.ts` mappe toute erreur non-200 vers ce message). Réflexe si ça arrive : vérifier que Docker Desktop tourne, puis `docker compose -f infra/docker/docker-compose.yml up -d`.
- Auth + rôles combinables (`User.roles: UserRole[]`, plus un seul `role`) — un utilisateur peut cumuler plusieurs rôles (ex. `AGENT`+`ADMIN` côté staff interne). `SUPER_ADMIN` reste un rôle de bootstrap plateforme, jamais attribuable via l'UI/API (seed/manuel uniquement).
- **Login sans identifiant workspace obligatoire** (2026-07-28) : `/login` ne demande plus que email + mot de passe. Le backend résout le tenant à partir de l'email (`AuthService.findTenantsForEmail`, boucle cross-tenant) — si un seul tenant correspond, connexion directe ; si plusieurs (même email dans plusieurs entreprises, cas rare), réponse `409 { requiresTenantSelection, tenants }` et le formulaire affiche un choix d'espace à cliquer. `tenantSlug` reste accepté en option dans `POST /auth/login` (rétro-compatible). Le cookie `workspace_slug` (pré-remplissage du champ, posé au signup) a été retiré, devenu inutile.
- **Page `/users`** (nouveau, 2026-07-28) : gestion des comptes du tenant du visiteur (`POST/GET /api/users`, déjà existant côté backend mais jusque-là non branché sur une UI). Sert deux publics selon qui la visite : un `ADMIN` d'une entreprise cliente y ajoute ses employés (toujours rôle `CUSTOMER`, pas de sélecteur — décision utilisateur "le plus simple possible côté client") ; un `ADMIN`/`SUPER_ADMIN` du tenant `INTERNAL` (TIC Harmony) y ajoute des employés avec un choix de rôles combinables Technicien (`AGENT`) et/ou Admin (`ADMIN`) via cases à cocher. Le backend (`UsersService.create`) est seul juge des rôles autorisés selon `tenant.type` (`CLIENT` → `{CUSTOMER}` uniquement, `INTERNAL` → sous-ensemble non vide de `{AGENT, ADMIN}`, `SUPER_ADMIN` toujours refusé) — le frontend n'adapte que l'affichage. Pas d'invitation par email : l'admin fixe le mot de passe initial directement. Pas d'édition/désactivation de compte existant pour l'instant (créer uniquement).
- Flow signup individuel fonctionnel (`/signup` → tenant mono-utilisateur, rôle `CUSTOMER`, slug auto-généré).
- Provisioning organisation via `POST /api/tenants` (réservé `SUPER_ADMIN`) — **UI ajoutée le 2026-07-28** : bouton "Nouvelle entreprise cliente" sur la page Directory (`/directory`, visible uniquement `SUPER_ADMIN`), ouvre un formulaire (nom, identifiant workspace auto-suggéré depuis le nom, premier admin) ; auparavant seulement accessible en appelant l'API directement (ainsi qu'ont été créés Acme Corp et Beta Corp).
- **Documentation** (ex-Base de connaissances) fonctionnelle : catégories + articles (FR/EN), filtrage par visibilité (`INTERNAL`/`PUBLIC`) selon le rôle, gestion admin (créer/modifier). Traduction EN pas automatique — copiée depuis le FR par défaut.
